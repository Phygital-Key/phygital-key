# Changelog

Changes to the base. Each product keeps its own changelog for its releases. Entries up to 0.3.0 describe the single program `phygital-key`, from before the split, and keep the names it had then.

## Unreleased

- **Agent-bound approvals (`pka.2`).** An agent that holds its own P-256 key can ask with it (`agent_key`). The approval then names that key (`cnf`), the person's passkey signs it with the request, and the page shows "Usable only by: whoever holds key ...". To use it, the agent sends a short proof signed with its key (`Phygital-Proof` header) naming the approval, the service and the request. A copy of the approval alone is refused (`PROOF_REQUIRED`), a wrong proof too (`BAD_PROOF`). `pka.1` approvals work as before; a service can require binding. In both verifiers (`verify_bound` in Rust, `verify(..., {proof, required})` and `signProof` in JavaScript), the gate, the demo service, the command line (`verify --proof`, `--require-binding`), MCP (`request_approval` with `agent_key`) and A2A (`agent_key` in the request). Spec section 7d. 18 new shared vectors (141 in all), a proof fuzz target.
- **Linux: the port is never free during a restart.** systemd now opens the gate's two loopback addresses (a `.socket` unit) and keeps them open while the gate restarts for an update; the gate takes them over. A program trying to take the port through two restarts never gets it (new secure-install check). macOS keeps the earlier defence: a program that takes the port during an update is stopped, 5 times at most, then the gate stops.
- **Security review 9** (agent-bound approvals and socket activation): 1 high, 2 low, 4 info, all fixed. The high one: the installer counted any process whose control-group path ended in `<program>.service` as the gate's own, and a user can name a unit of their own that way. See [security reviews](docs/security-reviews.md).
- **Tests for what had none:** the daily job's wait for standing approvals and its port takeover (`tests/update-job.sh`, 21 checks with stand-ins), staging a fresh file (review 7 L2), and in the products the waiting limit of 50, `audit-check` with a missing log or a damaged keyring, and `trust-service --key @file`.

## 0.5.0 (2026-10-18)

Released in Phygital Key MCP 0.5.0 and Phygital Key A2A 0.2.0.


- **Fix: the daily update job never ran from its service manager.** systemd and launchd start the job with no `HOME`, and the program stops without one ("no home folder found"), so automatic updates failed every day on Linux and macOS. Running `<program>-admin update` by hand worked. The units now set `HOME`, and the secure install test starts the job through systemd and launchd. Existing secure installs keep the broken unit until the next install, so run `<program>-admin update` once after the next release.
- **Fix: idle connections are closed after 10 seconds.** Before, a connection that never sent a request stayed open for good, and launchd gives a service 256 open files, so a program on the same computer could keep the approval page from loading by opening about 250 of them. Each connection now gets a 10-second header timeout (idle ones included), a failed accept waits and goes on, and both service files raise the limit to 8192 open files.
- **Release lists v2.** Each release also publishes `release2.txt`: the same files, plus when the list was signed and until when it is trusted (180 days, at most 400). An old list that a server keeps handing out now ends in "expired" instead of "up to date", and the secure install refuses a list signed earlier than one it accepted before (a rollback). `release.txt` stays for older installs.
- **A second, post-quantum signature.** `release2.txt` is also signed with ML-DSA-65 (FIPS 204, the RustCrypto `ml-dsa` crate) into `release2.txt.mldsa`. Once a product pins an ML-DSA key (`scripts/release-key.sh --pq`), the installed program requires both signatures for every update. A first install, which has no trusted program yet, checks the P-256 signature.
- **The Linux update service is sandboxed** like the gate: no new privileges, no devices, no kernel settings, no namespaces, only IP and local sockets. It keeps write access to the files it replaces.
- **New tests:** Google's Wycheproof cases for P-256 (746, in both verifiers) and ML-DSA-65 (210); a cross-check of every approval vector with SimpleWebAuthn, an independent WebAuthn library; edge tests from a new mutation-testing run (341 mutants, every real gap now caught); the installer's release-list check against lists signed with a test key (`tests/release-lists.sh`); ShellCheck on the installers and zizmor on the workflows; weekly 30-minute fuzzing per target. In the products: the approval page in Firefox and WebKit, abuse tests (floods, huge and slow requests), what the AI reads (plain text, no hidden characters), the update job run from systemd and launchd, and the systemd sandbox score.
- **Workflows:** Dependabot waits 7 days before suggesting a new version (security fixes skip the wait), Scorecard starts from no permissions, and the products publish releases with `gh` instead of a third-party action.

## 0.4.0 (2026-10-17)

- **Security review 8** (split, A2A, templates, sync): no critical or high findings. Fixed: the sync can only change the lock file and the template files, from a read-only test job; installers come from signed releases; the installer checks parent folders and refuses a 0.3 install next to it; every gate refuses any key-list audience; product values and read-only public routes are enforced.

- **One base, separate products.** This repository is now the shared base `Phygital-Key/phygital-key` (renamed from `phygital-key-mcp`): the verifiers, the gate engine, the spec, the test vectors, the examples and the shared docs. It publishes no programs and no releases; its releases 0.1.0 to 0.3.0 stay here as history. The products live in their own repositories and publish their own signed releases: [Phygital Key MCP](https://github.com/Phygital-Key/phygital-key-mcp) (program `phygital-key-mcp`, 0.4.0) and [Phygital Key A2A](https://github.com/Phygital-Key/phygital-key-a2a) (program `phygital-key-a2a`, new).
- **Gate engine library** `crates/phygital-key-gate` (was the program crate `crates/phygital-key`): the approval page, keys, standing approvals, receipts, audit log, secure install, signed updates and the shared commands. A product gives it a `Product` (name, program, id, version, repository, port, pinned release keys) and an `Adapter` (its agent protocol: routes under one path, optional public routes, optional stdio mode, connect and demo hints) and calls `phygital_key_gate::run`. The MCP server code moved to the MCP product.
- **Names per product.** The program name sets the data folder (`~/.<program>`), the environment prefix (`PHYGITAL_KEY_MCP_HOME`, `_PORT`, `_BIND`, `_ORIGIN`), the admin helper (`<program>-admin`), the secure-install user, folders and service labels (by product id, for example `_phygitalkeymcp`, `/Library/PhygitalKey/mcp`, `io.phygitalkey.mcp.gate`, `phygitalkey-mcp`, `/usr/lib/phygital-key-mcp`, `phygital-key-mcp.service`). Two products can be installed side by side. Every name per product: [reference](docs/reference.md#names-per-product).
- **Renamed commands and files.** `phygital-key mcp` is now `phygital-key-mcp stdio`; `mcp-token` is now `token`; `--open-mcp` is now `--no-token`; the access token file `mcp-token` is now `access-token`. A product without a stdio mode hides `stdio`.
- **Templates for product files.** The secure installer, the user installer, the secure-install CI test and the release scripts are templates in `crates/phygital-key-gate/assets/` with a `# BEGIN PRODUCT` block (and a `# BEGIN RELEASE KEYS` block) filled per product. A product writes its copies with the hidden command `<program> product-files --out .` (`install-service.sh`, `install.sh`, `tests/secure-install.sh`, `scripts/release-key.sh`, `scripts/package-manifests.sh`), and its CI fails if they differ from the templates. Release keys are pinned per product in its `release-keys.pem`, compiled into the program.
- **Daily sync.** Each product's `sync-base` workflow moves its `Cargo.lock` to the latest commit of the base's `main` branch every day, runs its tests and end-to-end checks, and only then pushes and starts its full CI. See [architecture](docs/architecture.md#the-base-and-the-products).
- **CI split.** The base CI runs the tests on Linux, macOS and Windows, the vectors check, the JavaScript checker, the examples, fuzzing and `cargo-deny`, plus CodeQL and Scorecard. The end-to-end checks, the secure-install test, the container check and the release workflow moved to the products. Removed from the base: `tests/e2e/`, `tests/secure-install.sh`, `.github/workflows/release.yml`, `packaging/`, `bucket/`, the root `install.sh` and `scripts/`.
- **Docs.** Shared docs stay here and are written for both products; the MCP-only guides (connect your AI app, MCP tools, agents guide, things to ask, agent prompts) moved to the MCP repository.

## 0.3.0 (2026-10-17)

- **Container image** `ghcr.io/phygital-key/phygital-key` (amd64, arm64), built by the release workflow from the signed release's Linux binaries, nonroot on distroless, with build provenance. Checked in CI on every push (builds, starts, enrolls). See [own server](docs/own-server.md#run-it-in-a-container).
- **Signed automatic updates:** the secure install checks GitHub once a day and installs a newer release only if its file list and SHA-256 sums (`release.txt`) are signed by a pinned release key. If the new gate fails its checks, the previous program comes back. It waits while standing approvals are active (a restart would end them), 7 days at most from the first wait on the installed version; waiting requests do not hold it back. `phygital-key-admin update --now` installs anyway. On by default; `--no-auto-update` turns it off, `phygital-key-admin update` updates now, `phygital-key-admin status` shows the last result. Every download (secure install, `install.sh`) now checks the signed list. New `phygital-key update` for installs in your own folders. The release key is a GitHub environment secret: after a `v*` tag push, the release workflow signs `release.txt` and publishes by itself; only repository admins can push `v*` tags, and the owner's approval step on the run is off for now (decision 36; one-time setup: `scripts/release-key.sh`). Each archive also gets a build record (`gh attestation verify`).
- **Security review 7** (signed updates, JavaScript stores, gate changes; 2 high, 3 medium, 3 low, 4 info): root now starts from a clean environment and every `curl` runs with `-q`, so a user's `~/.curlrc` or a fake program in their `PATH` never runs as root; a program that takes the gate's port during an update restart is stopped and the gate started again; only active standing approvals hold an update back; the two release-signing findings (M2, M3) were fixed with a key on the owner's computer and then superseded when the owner moved the key into GitHub, usable only from owner-only `v*` tags (decision 36); `phygital-key update` writes to a fresh file, and `audit-check` fails on a damaged keyring. See [security reviews](docs/security-reviews.md#review-7-signed-automatic-updates-js-stores-gate-changes).
- **JavaScript checker:** seen stores and use stores may now be async (a database): their answers are awaited, and anything but an exact `true` counts as already used. Before, an async store could let a replay through.
- **Fixes from the documentation review:** the MCP server names itself `phygital-key` with its version; the `next` text for an approved standing approval explains use tokens; the approval page states the end date and use cap after approving a standing approval, and shows "Revoked" after the revocation is signed; `audit-check` fails when the log is missing but a key is enrolled; `trust-service --key` accepts `@file`; an end-to-end check for the 30-a-minute flood limit.
- **Secure install:** `sudo phygital-key install-service` runs the gate as its own locked-down system user (launchd on macOS, systemd with hardening on Linux). Program owned by root, data readable only by the gate user, `phygital-key-admin` for enroll, token, keys, status and logs (each needs your administrator password). Tested for real on Linux and macOS in CI. `--uninstall`, `--purge`.
- **Signed revocations for standing approvals:** revoking stops new uses at once, then one more touch signs a revocation published at `/.well-known/phygital-key-revoked.json`; `verify_use` takes the checked list and refuses with the new code `REVOKED`. 5 new test vectors.
- **MCP access token** for HTTP mode (`serve`, `demo`): on by default, printed with the exact line to paste into an AI app, `phygital-key mcp-token`, `--open-mcp` to turn it off.
- **An independent JavaScript verifier** (`verifier-js/`, no dependencies, Node 20+ and browsers) that passes every shared test vector, in CI.
- **Two more independent security reviews**, every finding fixed: the gate now holds both localhost addresses (IPv4 and IPv6) and refuses to start if either is taken, and in `mcp` mode the page and MCP stop together, so no other program can serve a look-alike approval page; the secure install downloads and checks the official release itself (never runs or installs a file you could have changed), uses root-only folders, and refuses whenever another program listens on the gate's port; revocations can always be signed and retried and cannot be used to flood the gate; `serve` never writes secrets to its log; clean exit on SIGTERM; JavaScript checker fixes (built-in names as levels, byte-order marks, junk in revocation lists).
- **Docs:** a complete documentation set (guides for people, agents and services, internals, security and testing, use cases, runnable examples).
- **Credit:** `NOTICE` now reads "Created by Phygital-Key" and must travel with every copy (Apache-2.0, section 4(d)).

## 0.2.0 (2026-10-17)

- **Standing approvals:** approve once, with limits (exact fixed fields, integer ranges, short string lists, a use cap, up to 30 days). The gate signs a one-minute use token per action with a key it keeps only in memory; the service checks both with `verify_use` and counts uses. Revoke on the approval page. New tools `request_standing_approval` and `use_standing_approval`; new codes `NOT_ALLOWED` and `USED_UP`; 38 test vectors in `test-vectors/standing.json`. Integer limits need both `min` and `max`; standing approvals are always level high; receipts per use (`verify_use_receipt`).
- **Signed key list.** Every key added or removed is an approval signed by a key already trusted; the first key signs itself. `phygital-key keys --check <fingerprint>` checks a whole keyring from one pinned fingerprint. Keys can be removed from the home page (needs approval). Refetched keyrings must extend the copy accepted before (`--previous`), so old copies and forks by removed keys are refused; the origin is pinned by the checker. 25 test vectors in `test-vectors/keyrings.json`.
- **Used approvals remembered by the command line** (`seen-ids.jsonl`: locked, written through a temp file, fails closed if damaged), so `phygital-key verify` refuses a second use.
- **Fuzzing** of the verifier, the strict parser and the key history (`fuzz/`, runs in CI), and mutation testing of the verifier.
- **Signed receipts:** a service answers "done" or "failed" with a standard ES256 JWT that points at the approval by hash (AP2 style). The demo service returns them, the agent passes them back with the new `record_receipt` tool, and the gate shows "the service reported: done" only for receipts signed by a pinned service key (`phygital-key trust-service`). `phygital-key receipt-check` verifies them.
- **More edge test cases** from mutation testing: exact size limits (8192-byte request, 4096-byte client data, 16384-character approval), and five more key-history cases. 55 approval vectors in total.
- **Four independent security reviews** of the new code; all findings fixed (key-list rollback and forks, made-up receipts, double key removal, crash-safe used-ids file, save-then-swap keyring, strict receipt checks, standing ranges without a minimum, standing approvals kept until their end, reserved `standing` type, a cap on stored requests).
- **Installers:** Homebrew tap, a checksum-checking install script, and a Scoop bucket for Windows. winget manifests are generated in `packaging/winget/`.

## 0.1.0 (2026-10-17)

First public version. Pre-audit.

- `phygital-key-verify`: pure, offline verifier library in Rust.
- `phygital-key`: MCP gate (stdio and HTTP), approval page, enrollment with one-time links, add-key approval by an existing key, hash-chained audit log, command-line verifier, and a one-command demo.
